# Issues found in play testing

## 1. Tutorial: resources out of reach (fixed in eb3b472)
Found 2026-10-31. The tutorial's wood (and kit materials) spawn 15–30 m away; GPS drifts, so the player's position moves away from a node and it can't be picked up (tap range 30 m). Some nodes stay out of reach and the tutorial can't be finished from where the player stands.
Notes: nodes now spawn 8–15 m away (6 m apart), the pick-up range is 50 m during the tutorial only, "Collect from here" shows after 30 s and collects every remaining node of the step at once, and the nodes respawn around the player once they are all more than 60 m away.

## 2. Pocket mode keeps asking for location (fixed in e003535)
Found 2026-10-31. Tapping Enable shows "you need to enable location" although location is allowed for the app in the phone's settings; tapping again asks again, forever. Pocket mode needs background location ("Always" / "Allow all the time"), which the phone only grants in its own settings (and never in Expo Go); the code treats "while using only" as denied and repeats the same message.
Notes: cause on this setup was Expo Go (background location unsupported there, so the background request errors and reads as denied). Now the switch distinguishes no location / while-using-only / always: while-using turns Pocket mode on in limited mode with the platform upgrade steps and a settings button, no location keeps the message plus the settings button, Expo Go says it needs the installed app and never asks, and after a refusal the switch explains instead of asking again. Not testable without a real device: the actual system prompts and the settings round-trip.

## 3. Daily quests repeat the same kind (fixed in 64eaaac)
Found 2026-10-31. Two of the three daily quests are walking quests, which feels redundant. Quest picks are seeded by day and slot only, so two new games (or two players) on the same day get the same first quests.
Notes: variety rule is now kind-based (`questRules.variety` in `src/content/quests.ts`): a new quest picks a kind (Visit, Fight, Deliver, Gather, Trade, Walk) not already active while other kinds are unlocked; only when every unlocked kind is taken can a kind repeat, and then never Walk twice; within a kind it avoids the same objective as an active quest. Picks are seeded per player, day and slot (`playerSeed` on the save, mixed into the arrival, reroll, loot and target seeds), so two players or new games differ; only the tutorial's hand-over quest stays fixed. Rule added to `doc/design/quests/README.md`.

## 4. Repeated taps open the same screen several times (fixed in 954fbea)
Found 2026-10-31. When the app lags, tapping a menu button several times opens that many copies of the screen, stacked on top of each other.
Notes: all navigation now goes through one shared helper (`navigate` in `src/services/navigation.ts`, planning in `src/services/navigationPlan.ts`, lock in `src/content/navigation.ts`): a screen already on top of the stack does nothing, a screen lower in the stack is gone back to (`router.dismissTo`) instead of pushed again, and a navigation in progress ignores further taps on it for 500 ms (`tapLockMs`). Used by the island menu, the map's quest/debug/settings buttons, the team list and classes link, the settings tips button and tapped notifications. Hardware back (Android) and swipe back (iOS) are untouched — they use the stack's own back, not the helper. Issue 12 tightened this again: the tap lock alone still let queued taps stack screens when the JS thread was blocked.

## 5. Shop prices not showing (fixed)
Found 2026-11-01. In the smithy, and probably other shops, the coin icon shows but the price next to it doesn't. Happened before (fixed only in the Guild Hall, 4eae109), so it's a regression.

Fixed the same day. Cause: every shop data path was sound (an exhaustive probe found every price any shop can stock or buy finite and positive at every tier, and the English and French placeholders match), but each screen inlined its own `🪙 {price}` in a `space-between` row with no width guarantee for the number — the Guild Hall fix was never shared, and a missing price rendered as nothing after the coin with no signal. Now every shop price renders through the shared `PriceTag` (`src/components/PriceTag.tsx`): the number follows the i18n number format, the tag can shrink but never be crushed out of its row, and a bad price shows a visible `🪙 ?` with a warning in development. Tests pin the three guards: `src/game/places/shopPrices.test.ts` (every stock, buy and sell price finite and positive at every tier), `src/components/PriceTag.test.ts` (the number renders, the fallback is visible) and `src/i18n/placeholders.test.ts` (the English and French placeholders stay in step). Affected screens: the smithy, market, apothecary, hunting lodge, sawmill and mines, library, tavern recruits and stock, secret places (rare recruit, black market), the Guild Hall and every valuable sell list.

## 6. Some walking quests never progress (fixed in 223a4fa)
Found 2026-11-01. With four walking quests active at once, two completed normally and the other two stayed at "0 / 2,000 m" and "0 / 1,000 m" all day while the player walked.
Cause: quest progress was gated on `acceptedAt`, which is only set by `acceptQuests` when the quests list or map screen runs — quests that arrived while no screen was open never counted anything, and the walk baseline (`stepsAtAccept`) was captured at acceptance, losing the walk in between even for quests accepted later. Four walking quests at once was issue 3 (no variety rule).
Notes: walk, gather and patrol objectives now count from the moment the quest arrives (`counts` in `src/game/quests/progress.ts`), with the walk baseline (`stepsAtArrive`) captured at arrival in `newQuest`; every active quest of those kinds counts the same walk independently, in the app and in Pocket mode (the background watch follows arrival too), and progress survives restarts and daily resets. Place objectives still need the list opened, since that is what fixes their map target. Save version 30 (older saves reset).

## 7. Salvage has no confirmation (fixed)
Found 2026-10-31. Tapping Salvage destroys the item at once (only Rare, Legendary and infused pieces asked, via a plain system alert with no red warning). It is easy to lose a good item by mistake.

Fixed the same day: every salvage now asks first in an in-app dialog — the item's name and quality, what it gives back (materials with the Guild Hall bonus, gold, shards for an infused or Legendary piece), and a red warning when it is equipped on a hero, Rare or better, a restored relic, forged with a component or infused; Cancel changes nothing. The dialog's content is computed by `salvageDialog` in `src/game/forging/salvage.ts`.

## 8. Daily reset at 13:00 in New Zealand (not a bug)
Found 2026-10-31. Everything daily turns over at 00:00 UTC (`rotationRules.resetHourUtc: 0`), which is 13:00 in New Zealand, so a player who starts in the morning can get two batches of quests the same calendar day. Kept on purpose: one shared reset for every player.

Found 2026-10-31. Drawers, dialogs, modals, popovers and sheets only closed with their Close button; 16 components each hand-rolled a React Native `Modal` with a dimmed backdrop, and only ThreatDetail and WalkEffects answered a backdrop tap.

## 11. Pocket mode says "Location not allowed" when location is allowed (fixed)
Found 2026-11-02. On Android, with location set to "Allow only while using the app", tapping Pocket mode shows "Location not allowed". The phone's settings offer only while-using / ask every time / don't allow — "Allow all the time" is missing.
Cause: the local gitignored `android/` folder was generated before the `expo-location` plugin options (background location, foreground service) were added to `app.json`; `expo run:android` and gradle reuse it and never regenerate it, so the installed APK's manifest has no `ACCESS_BACKGROUND_LOCATION`, `FOREGROUND_SERVICE` or `FOREGROUND_SERVICE_LOCATION` — which also hides "Allow all the time" in the phone's settings. Without `ACCESS_BACKGROUND_LOCATION`, `Location.getBackgroundPermissionsAsync()` throws, and `getAutoGatherPermission`'s caller turned that into "denied" even though foreground location was granted, so Pocket mode showed the refusal dialog instead of starting in limited mode. CI release builds run `expo prebuild` on a fresh checkout and are not affected.
Notes: the foreground answer now alone decides "denied" — a background check or request that throws yields `'foreground'` (limited Pocket mode, with the Android upgrade steps dialog), with the error logged once in dev. `autoGatherRefused` is cleared whenever the phone reports foreground granted (`clearsRefusal` in `src/game/patrols/pocketPermission.ts`), so a wrongly refused player isn't stuck. `npm run android:fresh` (`expo prebuild --platform android --clean` then `expo run:android`) regenerates the stale folder, and `src/appConfig.test.ts` fails if the `expo-location` plugin options lose `isAndroidBackgroundLocationEnabled` or `isAndroidForegroundServiceEnabled`. Permission behaviour is pinned by `src/services/walkTracking.test.ts`.

## 12. Expeditions slow to open, and copies stack again (fixed in 8cbfce8)
Found 2026-11-02. The Expeditions screen takes seconds to open and to react to anything, and laggy taps still open several copies of a screen (issue 4 again).
Cause: two. The screen ran `estimateOdds` (300 simulated fights per dungeon) synchronously in a `useMemo` for every dungeon shown plus the overnight one, on mount and on every save or party write, plus two more per change in the Send dialog — blocking the JS thread for seconds while taps queued. And the navigation helper's per-target tap lock (500 ms) had expired by the time those queued taps ran, while the real stack (fed from a root-layout effect after the new screen renders) did not show the new screen yet, so each queued tap pushed another copy.
Notes: the odds are now computed off the first render — one dungeon per tick, only the selected tier's dungeons plus the overnight one shown, cards show "…" while their odds compute and the last known odds stay on screen in the Send dialog — behind a module-level cache (`src/game/expeditions/oddsCache.ts`) keyed by exactly what the odds read (dungeon, party with level, class, trait, roll, picks, gear and HP state by the minute, supply stock, meal and opt-in, briefing, blessing, Guild Hall ranks), so unrelated save writes (gold, materials, steps, expeditions, reports) cost nothing. The stack of screens is blocked by the optimistic stack plus the global pending lock: after any real push or back, every further navigate is ignored — any target — until the stack shows the target of the navigation in progress on top, or `navigationRules.pendingMaxMs` (3 s) passes; the pending lock lasts at least `tapLockMs`. Timings are pinned by `src/game/expeditions/oddsPerf.test.ts`, the cache by `src/game/expeditions/oddsCache.test.ts`, the lock by `src/services/navigationPlan.test.ts`.

## 13. Map panels lag for seconds, and Expeditions still opens twice (fixed in 1329be5)
Found 2026-11-02. Opening a map panel or Expeditions freezes the app for about 4 s; Expeditions can still open twice. Tapping a place on the map freezes the app for a few seconds before its panel opens; opening Expeditions for the first time freezes it for about 4 s; tapping again during that freeze can still open two Expeditions screens.
Notes: cause was fourfold. The place fight and patrol panels ran their odds estimate (a multi-hundred-fight simulation, the same as the Expeditions screen's) synchronously in a useMemo on open and on every save write; the navigation helper's pending lock could still open mid-freeze, because the real stack it waits for was overwritten by a stale report (the root layout fed it a fresh array every render) and its safety timeout counted wall-clock time from the tap, so taps queued through a 4 s block ran after every lock had expired; opening a panel re-rendered every marker on the map (they lived in the same component as the panel state, and the lists they were built from were recomputed every render); and the sky's clock woke JS twelve times a second on top, each frame flipping foliage layers through a setState. Fixes: the fight odds (place, patrol and Sanctum challenge) are behind the shared odds cache keyed by exactly what the run reads (`fightOddsKey` in `src/game/expeditions/oddsCache.ts`), computed one tick after the panel's first frame with "…" standing in and cached odds showing at once, so unrelated save writes cost nothing. The pending lock is released only by the real stack showing its target on top (the root layout passes the route names on only when they change by value, and a stale report opens nothing), its safety timeout is armed by the first `requestAnimationFrame` after the tap — a frozen thread runs no frames, so the lock holds however long the freeze — and every button that opens a screen stands down while a navigation is pending. The panels moved to their own store slice (`src/store/mapPanelsStore.ts`, rendered by `MapPanels`) with the markers in a memoised `MapMarkers` fed memoised lists and stable callbacks, so opening or closing a panel re-renders no marker; markers are culled to the visible bounds plus a quarter of the view per side (`cullingRules` in `src/content/map.ts`, pure rule in `src/game/generation/culling.ts`, bounds read at the end of a pan or zoom, the selected patrol and the open panel's place always drawn), and panning no longer re-renders the map screen at all. The sky's clock runs natively (re-armed once per ten minutes), and the decorations hide below zoom 17, stand as one still frame from 17 to 18 with every animation timer stopped (paused while a panel is open too), and sway only from 18 up without re-placing the plants. A release-build profiler sits behind the debug screen's "Record timings" switch (`src/services/timings.ts`): the slowest 50 spans, logged with the `[perf]` tag, timings for the map's computations, the markers' and panels' renders, the odds, and the wait from a tap to what it opens; `src/perf/timings.test.ts` logs the numbers (a place fight's odds cost ~15–70 ms per estimate on a development machine — now off the first frame and cached).

## 15. After one screen, no screen opens any more (fixed in 00fe4c6)
Found 2026-11-01. After navigating once, no further screen opens: taps on the island menu, the settings or debug buttons do nothing, and even waiting does not clear it.
Notes: the layered locks from issues 4, 12 and 13 deadlocked. The global pending lock waited for the real stack (mirrored from `useRootNavigationState` in the root layout) to report the target on top; when that report never matched, the lock never cleared. Its safety timeout only expired inside `planNavigation`, which only runs when `navigate()` is called — but the menu buttons were disabled while `navigationPending()` held, so nothing ever called `navigate` again. The custom lock is gone entirely: every stack screen is declared singular (`dangerouslySingular` on each `Stack.Screen` in the root layout, and `router.push(href, { dangerouslySingular: true })`), so expo-router's own navigator state reducer guarantees one copy per screen (dynamic segments resolved from params, so `team/[heroId]` is singular per hero) and a push to a screen already in the stack filters it out of the history instead of stacking a copy. `navigate` (`src/services/navigation.ts`) is now a thin wrapper whose only guard is the tap lock: a second call for the same href within `tapLockMs` (500) is ignored — a pure timestamp comparison that cannot lock anything; a different href is never swallowed. Removed: the pending lock, `armPending`, `requestAnimationFrame`, `navigationPending`, `onNavigationChange`, the stack mirror, the `dismissTo` branch, `setNavigationStack`, the `useNavigationPending` hook and its uses (the menu buttons are never disabled), `navigationPlan.ts` and its test, and `pendingMaxMs`. Hardware back, iOS swipe back and notification taps go through the normal stack and are unaffected. Tests pin the tap lock and the singular layout in `src/services/navigation.test.ts`.

## 19. A tier 2 material (stone) dropped for a tier 1 player (fixed)
Found 2026-11-01, after 0.7. A player still on tier 1 received stone as a reward; stone is tier 2's main material (the wooden pickaxe, the tier 1 boss reward, is what opens it).
Cause: a materials drop picks one option from its source's theme (`lootConfig.materialThemes`, `patrolThemes`). The "cache" option draws only ores the player's pickaxe can mine, but the fixed lists were taken as they stood, and the ruins dig lists `stone` outright, so a dig on tier 1 (ruins spawn from the start) could give stone.
